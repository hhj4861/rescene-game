## 우선 수정할 문제

### P1-01 · 메이: 겹친 방향키를 떼면 아직 누른 방향도 멈춤

- 재현: 메이 생존전 → 왼쪽 키 유지 → 위쪽 키도 누름 → 위쪽만 놓고 왼쪽 유지.
- Chromium/WebKit 모두 `(170, 290)` 부근에서 이동이 멈췄다. 1.2초를 더 진행해도 위치가 같고 이동 상태가 0이었다. 왼쪽을 떼었다 다시 누르면 x≈42까지 이동했다.
- 원인: `app.js`의 `held`가 마지막 입력 하나만 기억하고 `releaseMovement`가 이를 해제한다. 계속 눌린 다른 키로 돌아가지 않는다. Playwright의 keydown/keyup을 사용했고 OS 자동 반복은 생성하지 않았다.
- 권장: 눌린 키/포인터를 각각 관리하고 마지막 방향을 놓으면 남은 방향으로 복귀한다. 대각선 이동을 새로 추가할 필요는 없다. 정지·탭 이탈 시에는 전체 입력을 비운다.
- 통과 기준: 왼쪽 유지→위 누름/해제 후 왼쪽 재개, 반대 순서, WASD, 방향+대시, 정지/복원에서 입력이 멎거나 남지 않을 것.
- 근거: `input-exploration.json`; `src/arcade-room/app.js`의 pointerdown, releaseMovement, keydown 처리.

### P1-02 · 가로 모바일과 낮은 PC에서 게임판·버튼이 화면 밖으로 내려감

- 844×390 최상단 측정: Chromium 게임판 하단은 펌프 516.5 / 원이 743 / 메이 707 / 제나 743 / 리브 699.5px. 버튼 하단은 561.5–853px다. WebKit에서도 다섯 게임 모두 같은 문제가 있다.
- 1280×720 PC에서도 원이 버튼 하단 842.5, 메이 806.5, 제나 890.5, 리브 806.5px. 키보드를 써도 게임판 전체를 동시에 볼 수 없는 게임이 있다.
- 원이 가로 화면은 실제 모바일 모드로도 재현했다. 시작 시 세로 화면 밖에 있는 판을 스크롤하면 상단 상태를 잃는다.
- 권장: 화면 폭뿐 아니라 높이/가로 방향을 기준으로 별도 배치를 적용한다. 액션 게임은 조작부를 판 옆에 배치하고 소개·설명을 접는다. 퍼즐은 터치 칸을 더 작게 만들기보다 판 스크롤과 고정 도구줄을 쓴다.
- 통과 기준: 844×390, 1280×720에서 액션 게임의 필수 영역/조작이 동시에 보이며 결과·정지·강화창도 접근 가능할 것.
- 근거: `browser.json`, `focused.json`, `chromium-844-*.png`, `chromium-1280-*.png`. 1280폭 캡처 파일은 마지막 720높이 실행본이며 900높이 수치는 JSON에 구분되어 있다.

## 난이도와 발견성 개선 후보

### P2-01 · 원이: 세 길 도장을 먼저 모으면 초반은 여전히 오래 손을 떼도 클리어

- 이전 ‘첫 노래만 먹고 멈춤’ 정책은 1–5단계 모두 0/20으로 개선됐다. 적극적 이동/회피 정책은 검사한 10개 단계 모두 20/20으로 통과했다.
- 추가 정책: 세 길 간식과 첫 노래를 획득할 때까지만 이동/공격하고, 이후 모든 입력을 중단한다.
- 1단계는 20판 중 19판이 입력 중단 후 클리어했다. 나머지 1판은 중단 전에 이미 클리어했으므로 무입력 승리로 세지 않았다. 중단한 19판은 평균 15초부터 멈추고 평균 약 53초를 더 무입력으로 진행했다.
- 같은 조건의 중단 후 승리: 3단계 15/20, 5단계 4/20, 10단계 2/20, 20단계 0/20. 3단계에도 중단 전 클리어 1판이 있어 총 승리 16/20과 구분한다.
- 판단: 도장 수집이 초반 이동은 유도하지만, 이후 도움 효과가 전투·간식 수집을 지나치게 대신할 가능성이 있다. 초보자용 1단계의 관대함 자체를 버그로 보지는 않는다.
- 권장: 노래와 멤버 도움은 유지하면서 구간별로 다시 길 선택/회피할 이유를 만들고, 고정 위치의 자동 수집에는 빈도를 제한한다. 단순 생명/속도 상향은 피한다.
- 근거: `focused.json`, `followup.json`, `walk.js`의 노래 지원·간식 유인·별이 보상.

### P2-02 · 메이: 단계별 기본 무기 강화 때문에 난이도가 고르게 증가하지 않음

- 동일 순환 이동+성장 선택 정책: 5단계 8/20 → 6단계 18/20 → 10·11단계 20/20 → 20단계 10/20 → 30단계 6/20.
- 이동 없이 강화 선택만 하는 정책도 11·15단계 각각 4/20을 클리어했다. 강화 선택은 했으므로 완전 무조작이라고 부를 수는 없다.
- 능동 회피/경험치 정책은 검사한 1–5·10·20단계에서 각 20/20. 이전 고단계 생존 불가 문제는 완화됐다.
- 원인 후보: 6단계부터 기본 별빛 2, 8단계부터 기본 방울 1, 11단계부터 기본 별빛 3이 즉시 주어진다. 적 체력/속도와 플레이어 시작 성장치의 계단이 서로 다르다.
- 권장: 보상과 적 압력을 같이 조정하고 5→6, 7→8, 10→11 경계를 집중 비교한다. 숙련 정책의 100%만으로 ‘너무 쉬움’을 단정하지 않는다.
- 근거: `simulations.json`, `followup.json`, `may-survival.js:createSurvival/survivalDifficulty`.

### P2-03 · 펌프: 1→2단계 노트 밀도와 실패 압력이 급증

- 1단계는 격박, 2단계는 매박 노트로 바뀌어 기본 밀도가 약 두 배다. 시작 생명은 50%, 미스마다 -12%로 같다.
- 정확한 타이밍에 80%만 무작위로 입력한 정책: 1단계 12/20 완주 → 2단계 5/20 → 4단계 3/20. 90% 정책은 검사 단계 모두 20/20이다. 실제 사람의 적중률/승률이 아니다.
- 실제 YouTube의 새 판을 아무 입력 없이 시작했을 때 영상 재생 상태와 시간 진행은 확인됐고, 약 6초 게임 진행 후 생명 소진으로 끝났다. 첫 실패까지 익숙해질 시간이 짧다.
- 권장: 연습/초급의 생명 완충이나 1→2단계 사이 밀도 단계를 검토한다. 동시 화살표와 빠른 박자 안내를 도입 전에 제공한다.
- 근거: `followup.json`, `input-exploration.json`, `model.js:makeRhythmNotes/stepPump`.

### P2-04 · 리브: 숙련되어도 첫 아이템 후 120초를 기다려야 보스 등장

- 적극적인 게이트/아이템/공격 정책은 검사 단계 모두 20/20. 평균 클리어는 1단계 127.2초, 30단계 131.0초로 비슷하다.
- `runner.js`는 첫 아이템 획득 후 120초가 지나야 보스를 생성한다. 게임이 어려워졌다기보다 고정 대기가 길어지는 구조다.
- 권장: 처치·성장 목표를 충족하면 보스를 일찍 부르거나, 남은 등장 시간을 명확하게 보여준다. 노래 재생 보장과 보스 소환 조건은 함께 설계해야 한다.
- 근거: `simulations.json`, `runner.js:32`.

## 한계와 검증 도구 메모

- 66개 회귀 통과는 모든 조작 조합이나 재미를 보장하지 않는다. 탐색에서 새로 찾은 실패 조건은 기존 테스트에 없었다.
- 난이도 수치는 모델 입력 정책의 결과이며 사람의 승률/반응 시간/연속 스테이지 경험이 아니다. 모델 실행은 실제 오디오 길이가 보상 상태에 미치는 모든 UI 동작을 재현하지 않는다.
- 일반 영상 회귀/레이아웃은 YouTube API 대역을 사용했다. 별도 1회만 대역 없이 실제 YouTube 영상 시작 상태와 게임 시계 진행을 확인했다. 청음·영상 전체 완주·실기기 오디오 지연은 미검증이다.
- 추가 네이티브 다중 터치 탐색은 손가락 종료 이벤트의 의미를 충분히 검증하지 못했고, 상단 경계에 도달한 위치 정지를 입력 해제와 구분하지 못했다. `touch-exploration.json`은 참고 자료이며 확정된 터치 결함/통과 증거에 넣지 않았다.
- `focused.mjs` 최초 실행은 영상 게임에만 있는 `.game-info`가 원이에도 있다고 가정해 실패했다. nullable 선택자로 고치고 재실행했다. 이는 제품 오류가 아닌 감사 도구 오류다. `focused-failed.log` 보존.
- 다음 구현 순서: P1 입력/배치 → 원이·메이 난이도 경계 → 펌프·리브 진행 속도. 수정은 별도 worktree에서 진행하고, 같은 조건 재현 검사 후 실제 휴대전화 조작감을 확인한다.
