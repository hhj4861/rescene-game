# 리센느 오락실 UX·난이도 검증 — 2026-10-10

운영 게임은 기본 동작을 유지하지만, 모바일 화면 구성과 게임별 난이도 균형에 개선이 필요하다. 먼저 모바일 리브 화면과 안내 중 게임 진행을 수정하고, 원이의 무조작 클리어·제나의 밀대 의존·메이의 고단계 성장 곡선을 조정하는 것을 권장한다.

이번 작업은 **검증만 수행**했다. 게임 코드 변경·운영 배포는 하지 않았다. 이 문서는 검증 결과이며 아래 수정안은 아직 구현되지 않았다.

## 발견 사항

### UX-01 · 높음 — 모바일 리브의 주인공과 조작 버튼이 첫 화면 밖에 있음

- 재현: 모바일 390×844에서 리브 진입 후 노래 아이템 활성 상태를 열고 페이지 최상단을 본다.
- Chromium: 게임판 y=495–950.5, 조작 버튼 하단 y=1018.5. WebKit도 게임판 y=487–942.5, 버튼 하단 y=1010.5다. 캐릭터와 좌우 조작 버튼이 844px 화면 밖에 있다.
- 320×568에서는 게임판 y=382–693, 버튼 하단 y=747이다. 펌프도 이 작은 화면에서는 게임판 하단이 y=645로 넘어간다.
- 스크롤하면 플레이할 수 있으나 시작 직후 캐릭터·버튼을 찾기 위해 화면을 움직여야 한다. 영상과 목숨, 전체 게임판, 조작 버튼을 동시에 볼 수 없다.
- 원인: 영상 높이와 상단 정보, 게임판 세로 비율이 누적된다. 리브는 모바일에서 영상이 하트 아래에 배치되지만 게임판 높이 계산은 그 공간을 충분히 반영하지 않는다.
- 근거: `src/arcade-room/style.css:151`, `:173` 이후 모바일 grid; `browser.json`, `chromium-390-catch.png`, `webkit-390-catch.png`, `chromium-320-rhythm.png`.
- 권장: 현재 영상 위치를 유지하되 작은 화면에서 접힌 재생 바를 기본으로 제공하거나, 플레이 영역과 조작 버튼을 기준으로 높이를 배분한다. 단순히 게임판을 더 작게 만드는 것은 피한다.
- 통과 기준: 320×568과 390×844에서 최초 화면에 주인공·필수 조작이 보이고, 전투 중 스크롤 없이 전체 플레이 영역을 확인할 수 있어야 한다.

### UX-02 · 높음 — ‘게임 안내’를 읽는 중 펌프가 게임 오버됨

- 재현: 모바일 펌프 시작 → `게임 안내 ⓘ` → 아무 입력 없이 설명을 읽는다.
- 확인: 열기 직후 `playing / 60초 / LIFE 50%`. 12초 가상 시계 진행 후 `result / 54초 / LIFE 0% / 게이지 소진 · GAME OVER`. 약 6초의 게임 진행만으로 실패했다.
- 원인: `mountGameInfo`는 팝오버만 열고 시계를 멈추지 않는다. 동시에 팝오버가 열려 있으면 전역 키보드 게임 입력은 무시한다.
- 근거: `src/arcade-room/game-info.js:18`, `src/arcade-room/app.js:234`; `guide-check.json`, `guide-during-play.png`.
- 권장: 안내를 열면 게임·음악 시계를 함께 일시정지하고, 닫을 때 이전 진행 상태에 맞게 재개한다. 원래 일시정지 상태라면 임의로 재개하지 않는다.
- 통과 기준: 안내를 30초 읽어도 시간·목숨·게이지·노트 판정이 바뀌지 않아야 한다. ‘하는 방법’과 ‘게임 안내’의 정지 동작도 일관되어야 한다.

### BAL-01 · 높음 — 원이는 첫 노래 이후 무조작으로 대부분 진행됨

- 재현 정책: 첫 노래 아이템이 보이면 그 길로 이동하고 획득 전까지만 공격한다. 획득 후에는 이동·공격·점프 등 모든 입력을 중단한다.
- 1–5단계는 각 **20/20 클리어**, 10단계 **18/20**, 20단계 **14/20**. 1단계 평균 종료 시간은 36.3초다.
- 원인: 노래 중 모든 간식이 플레이어 길로 이동하고, 멤버가 몬스터 공격·장애물 제거를 수행한다. 간식 3개마다 별이 공격, 연속 5개마다 무적에 해당하는 효과도 이어져 수동 조작의 필요가 줄어든다.
- 근거: `src/arcade-room/walk.js:49`–59 및 간식 보상 처리; `followup.json`의 `first-song-then-idle`.
- 권장: 멤버 도움은 유지하되 간식 유인을 일정 간격·범위·횟수로 제한하고, 플레이어가 길을 고르거나 회피해야 하는 상황을 남긴다.
- 통과 기준: 도움 효과를 받은 적극적 플레이는 유리하되 첫 곡 이후 무조작 정책이 연속 스테이지를 안정적으로 클리어하지 못해야 한다.
- 참고: 파이리 2단계는 적극적 플레이의 3단계 이상에서 실제 도달했다. 1–2단계는 클리어가 빨라 진화 전에 끝났으며, 기능 누락으로 판단하지 않는다.

### BAL-02 · 중간 — 제나의 5단계 이후 숨은 빵은 계속 판 전체를 차지하는 1개

- 생성 결과: 1단계 2개 → 2단계 3개 → 3단계 1개 → 4단계 2개 → **5–20단계 모두 1개**.
- 원인: 첫 영역을 판 전체 크기로 만든 후, 그 영역과 겹치지 않는 추가 빵을 배치하려 한다. 빈 공간이 없으므로 목표 개수가 증가해도 추가 배치에 실패한다. 최대 판 크기가 8×8이어서 11단계 이후도 동일하다.
- 근거: `src/arcade-room/bakery-hunt.js:15`–24; `simulations.json`의 `bakery`; 운영 11단계 화면에도 `0 / 1 십원빵`으로 표시된다.
- 권장: 전체 판 1개인 도전 스테이지와 여러 작은 영역을 찾는 스테이지를 구분해 배치한다. 빵 개수와 영역 크기가 실제 생성 결과에 반영되는지를 검증해야 한다.
- 통과 기준: 5단계 이후에도 명시한 패턴대로 작은 빵 여러 개와 큰 빵이 번갈아 나오며, 목표 개수와 생성 개수가 일치해야 한다.

### BAL-03 · 중간 — 제나는 퍼즐 매치보다 무료 밀대로 지우는 비중이 높음

- 기존 테스트의 플레이 정책을 그대로 사용했다. 필요한 빵 영역의 줄에 밀대가 있으면 사용하고, 없으면 남은 매치 중 보상에 유리한 교환을 선택한다.
- 확인한 10개 단계 × 20시드 모두 클리어했다. 지운 칸 중 **66.4–72.8%가 밀대 사용**이었다. 생각하는 시간을 제외한 모델 진행 시간은 평균 1.7–3.9초다. 이를 사람의 클리어 시간으로 해석하면 안 된다.
- 원인: 매치 가능한 교환이 없으면 무료 밀대가 즉시 지급된다. 그 밀대로 한 줄을 지워도 매치가 없으면 또 지급된다. 교환 횟수도 소비하지 않는다.
- 근거: `src/arcade-room/model.js:79`, `breadAction`의 밀대 처리; `tests/helpers/bakery-player.mjs`; `simulations.json`.
- 판단: 막힘 방지 장치는 정상 작동하지만 후반이 ‘퍼즐 해결’보다 ‘남은 줄 지우기’가 된다. 버그라기보다 현재 유한 퍼즐 규칙의 난이도 문제다.
- 권장: 보충 퍼즐 없이 남은 칸으로 풀어야 한다는 요구를 유지하면서, 생성 시 해결 가능성을 보장하고 막힘 보조는 고립된 소수 칸에 한정한다. 무료 밀대만 없애면 진행 불가 상태가 생기므로 함께 설계해야 한다.

### BAL-04 · 중간 — 메이의 고단계는 성장하기 전에 압박이 커짐

- 단순 경로 순환 정책은 1단계 13/20, 3단계 11/20, 5단계 0/20이었다. 이는 회피 정책이 약해 생긴 차이도 있어 추가 검증했다.
- 적·탄환을 피하고 가까운 경험치를 수집하며 성장·대시를 사용하는 추가 정책은 1단계 19/20, 3단계 20/20, 4단계 19/20, 5단계 17/20이었다. 그러나 **10단계 0/20(평균 11.1초), 20단계 0/20(평균 8.4초)**였다.
- 원인: 매 스테이지 공격은 별빛 1레벨로 초기화되지만 적 체력·이동 속도·등장 빈도는 동시에 올라간다. 1단계 기본 적 체력 1, 등장 간격 0.9초에서 10단계 체력 4, 간격 0.45초로 변한다. 초반 공격력은 1, 발사 간격은 0.55초로 그대로다.
- 근거: `src/arcade-room/may-survival.js:5`–6, `:25`–28; `followup.json`의 `avoid-and-collect`.
- 권장: 단계별 시작 성장치, 시작 직후의 완화 구간, 적 체력과 물량 상승 시점을 분리해 검토한다. 실제 연속 플레이는 목숨도 이어받으므로 목숨 3으로 시작한 이번 테스트보다 불리할 수 있다.
- 제한: 해당 정책의 실패가 사람의 클리어 불가능을 증명하지는 않는다. 다만 초반 성장 기회가 급격히 줄어드는 구조는 확인했다.

### UX-03 · 중간 — 제나 최대 판의 모바일 터치 칸이 작음

- 8×8 개별 칸: 320px 화면 약 **29.1px**, 390px 화면 **36.75px**. PC 1280px에서는 약 44px이다.
- ‘판 확대’로 크게 볼 수 있지만 확대 후 스크롤과 두 번 탭 방식으로 조작이 바뀐다. 작은 화면에서 처음부터 정확한 드래그가 필요한 점은 불편할 수 있다.
- 근거: `browser.json`의 photo `tile`, `chromium-390-photo.png`.
- 권장: 작은 화면은 탭 선택·교환 피드백을 더 명확히 하고, 게임판에 쓰지 않는 상하 여백을 줄이거나 확대 상태의 조작을 안내한다. 실기기 엄지 조작을 추가 확인해야 한다.

## 정상 확인과 검증의 한계

- 20개 브라우저 조합에서 문서 가로 넘침 0, JavaScript `pageerror` 0. PC 1280×900에서는 다섯 게임의 게임판과 기본 조작이 세로 화면 범위에 들어왔다.
- 리브 모바일 영상은 하트 아래, 펌프 영상은 생명 게이지 위에 있다. 배치 순서는 요청대로지만 모바일 가용 높이 문제는 남아 있다.
- 203개 단위 테스트가 모두 통과했다. 테스트 통과가 균형 잡힌 난이도나 재미를 의미하지는 않는다.
- 기존 PR #33 운영 검증의 57개 브라우저 통과 기록은 이전 배포 기록에 있다. 이번 실행 횟수에 합산하지 않았다.
- 제나 외 게임의 모델 `isStageClear`는 UI가 매 프레임 호출하는 것과 같은 조건으로 종료했다. 제나는 모델의 애니메이션 종료 대기까지 사람 체감 시간으로 측정하지 않았다.
- 시뮬레이션은 각 단계를 독립적으로 목숨 3에서 시작했다. 실제 연속 스테이지·성장 선택 성향·반응 시간에 따른 체감 차이는 남는다.
- 이번 확인은 새 메이 생존전을 대상으로 하며 백업 보글보글의 신규 UX 감사는 포함하지 않는다.
